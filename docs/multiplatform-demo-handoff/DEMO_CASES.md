# 两个个性化授权表 Demo 案例

## 使用方式与演示边界

以下两份表格参考“初次授权书”的区块结构，模拟用户已经填写并确认的结果。它们用于演示**个性化需求采集、商品检索及跨平台比价**，不是现有后端可执行的付款授权。

当前 `/agent` 页面尚未逐项呈现完整授权书 UI；演示时可先展示下列模拟授权表，再把每份表末尾的“当前结构化表单转录值”录入 `/agent`。`/agent-risk` 仍只支持独立沙盒商品 `sandbox-lotion`，不要用它为下面两种护肤品付款。

金额均为 HKD 元。软边界表示超过后必须再次向本人确认；硬边界表示不可突破。由于本 Demo 不执行付款，预算字段仅用于需求筛选和说明预期风控规则。

## 演示步骤与成功判定

1. 打开 `http://localhost:3000/agent`，点击“开始新任务”。
2. 展示对应的模拟授权表。若模型已配置，可先把该 Case 的自然语言需求发送给 Agent；随后把结构化表单转录值填入页面进行校正。若模型未配置，直接填写结构化表单。
3. 点击“保存需求并校验”；如页面列出缺失字段，只补充系统实际支持的内容，不把模拟授权表未接入的字段宣称为已生效。
4. 点击“运行 Shopping 搜索与审核”。第二个 Case 必须重新创建任务。
5. 页面应展示需求版本、实际 Shopping 请求和审核结果。`needs_verification` 是缺少实时结账事实时的预期状态。

候选排序会受筛选和评分影响，不承诺 UI 前三名一定是同一商品的三个报价。要确定性核对三平台报价，请调用：

```powershell
Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/products/search" -ContentType "application/json" -InFile ".\examples\multiplatform-moisturizer.request.json"
Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/products/search" -ContentType "application/json" -InFile ".\examples\multiplatform-toner.request.json"
```

目标候选的 `candidate.merchant.platformId.value` 应覆盖 `watsons-hk`、`sasa-hk`、`mannings-hk`；同一商品的 `productId`、`skuId` 相同，`offerId` 不同。未配置 LLM 时状态可能是 `partial`，不表示数据库读取失败。
